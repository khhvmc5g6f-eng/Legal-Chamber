# Defects found in the router/jurisdiction files themselves, M1-KESTREL

Found by actually using the files against this matter, not by inspection for its own sake.

## 1. Dangling cross-reference: `skills/legal-work/SKILL.md` Step 1 points to a taxonomy that isn't in the file it names

Step 1 says: "Matter type ... See `../../docs/OPERATING_RULES.md` for the full taxonomy the specialist skills below assume." `docs/OPERATING_RULES.md` was read in full and grepped for "taxonomy" and "matter_type" - neither term, nor any matter-type list, appears anywhere in that file. The actual taxonomy that exists is the `matter_type` enum in `schemas/matter.schema.json` (`research, litigation, administrative-public-law, criminal, employment, regulatory, transactional, advisory, negotiation-adr, academic`) and the same list restated inline in `SKILL.md` itself - `OPERATING_RULES.md` has no such section. This is a broken pointer: anyone following the router's own instruction to go find "the full taxonomy" in `OPERATING_RULES.md` will not find it there.

## 2. `scripts/deadline_calculator.py` has no month-denominated mode, but the jurisdiction this matter actually uses is month-denominated at its core

Confirmed live against `legislation.gov.uk`: both the ERA 1996 s.111 unfair-dismissal time limit and the Equality Act 2010 s.123 discrimination time limit run in calendar months ("period of three months beginning with..."), not days. `deadline_calculator.py --help` confirms `--unit` accepts only `calendar` or `business`, both of which are day-counted; there is no month unit. This forces any real use of the tool for an England & Wales employment matter into an approximation (e.g. treating "three months" as 92 days), which is not equivalent to true calendar-month arithmetic and can be off by several days depending which months are spanned (they range 28-31 days) - see `procedure/limitation.md` for the illustrative run actually done. This is a real functional gap in the one deterministic tool the litigation skill mandates be used instead of memory for exactly this kind of calculation, distinct from the "no routing-table row for a bare deadline request" gap `docs/HONEST_STATUS.md` already lists.

## 3. `jurisdictions/england-wales/README.md` names the Employment Tribunal in its hierarchy but never mentions the ACAS Early Conciliation precondition at all

The pack's "Governing statutes/codes" section names the Employment Tribunals Rules of Procedure but not the Employment Tribunals Act 1996 (s.18A of which makes ACAS Early Conciliation a mandatory precondition to almost every ET claim) and does not mention ACAS or Early Conciliation anywhere in the file. Given that a mishandled or unconsidered ACAS EC step is one of the single most common ways a genuine ET claim is lost on a technicality, and this exact matter turns on it, this is a real content gap in the pack, not a hypothetical one - worth recording even though the pack is honestly labelled `STRUCTURAL_DRAFT` and does not claim completeness.

## 4. `employment` exists as a first-class `matter_type` in the schema but has no matching row or specialist skill

`schemas/matter.schema.json` treats `employment` as a distinct value from `litigation`, `regulatory`, etc., but `skills/legal-work/SKILL.md` Step 4's routing table has no row for it and `skills/` has no `legal-employment/SKILL.md`. In practice this matter still routes correctly through the generic `litigation`/`evidence`/`research`/`draft` rows, so it is not a blocking defect, but it means the schema draws a distinction the router and skill set do not actually act on anywhere - worth flagging under the repo's own "grows by depth, not breadth" principle (`CLAUDE.md` rule 6) rather than leaving the mismatch implicit.

## 5. `schemas/chronology.schema.json` requires `date` on every event, with no way to represent "known to exist, zero date information at all"

Found while actually building `chronology/chronology.json` from the fact ledger. The schema makes `date` a required field (type `string`, described as "ISO date. If only approximately known, use `date_certainty`..."), and `date_certainty` includes an `UNKNOWN` enum value - but `UNKNOWN` only qualifies *how firm* a date is, it does not let you omit the date itself. Several events this matter's facts assert exist (the alleged protected disclosure(s), the disciplinary process's own internal dates, the OH referral(s), the sickness absence period(s), the contradictory emails, and ACAS EC "Day A") carry literally no date information whatsoever - not even an offset like the ones given for dismissal and the EC certificate. There is no schema-conformant way to add a chronology record for these: either the event is left out of the timeline entirely (what `chronology.json` does here, with the omission itself logged in `chronology_gaps.md`), or a non-ISO placeholder string like `"date": "UNKNOWN"` is put in a field the schema's own description says is an ISO date - which is technically valid (the field is an unconstrained string, no `format: date`) but semantically dishonest against what the field claims to hold. Since `fact.schema.json`'s `date_certainty: UNKNOWN` already exists precisely for this situation at the fact level, the chronology schema's inability to carry the same "no date at all" case through to the timeline is a real, non-hypothetical gap for exactly the kind of disputed-chronology matter this skill exists to handle.

## 6. `schemas/issue.schema.json`'s single-value `burden` enum per element cannot represent the Equality Act 2010 s.136 two-stage shifting burden without splitting one legal test into two schema elements

Found while building `issues.json` for the five Equality Act-based heads (ISS-005 to ISS-008), all of which are governed by the s.136 mechanism: the claimant first shows facts from which a tribunal could conclude discrimination in the absence of an explanation (an `EVIDENTIAL` burden on the claimant), and only then does the burden shift to the respondent to prove the contrary (effectively a `REVERSE` burden) - one legal test, two burden-bearers, at two different stages. `elements[].burden` accepts exactly one of `LEGAL`/`EVIDENTIAL`/`REVERSE`, so there is no way to record this as a single element faithfully. The workaround used here was to split it into two separate `elements` entries (e.g. ISS-004's "detriment" element as `EVIDENTIAL` and its "causal link" element as `REVERSE`) - which works, but means the issue tree's element count no longer maps one-to-one onto the substantive legal ingredients of the cause of action; a reader comparing the tree against a textbook statement of the s.136 test would need to know this split is an artefact of the schema, not of the law.
